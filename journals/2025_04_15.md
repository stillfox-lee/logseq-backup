	- > In this paper, we present AlphaCodium, a code-oriented
	  flow that revolves around an iterative process where we re-
	  peatedly run and fix a generated code against input-output
	  tests.
	- AlhpaCodium 流程中的关键要素：
		- 生成额外的数据。例如problem reflection和test reasoning
		- 用额外的 AI 生成的测试丰富公共测试集
	- 主要流程:
	  ![](https://raw.githubusercontent.com/stillfox-lee/image/main/picgo/202504151049649.png)
		- **Pre-processing** 阶段
			- 主要以自然语言推理 problem。
			- **Problem reflection**
				- 以**要点**形式描述问题，涉及问题goal、input、output、rule、constraints以及问题描述中出现的其他相关细节。
				- 一个典型的问题：
				  ![](https://raw.githubusercontent.com/stillfox-lee/image/main/picgo/202504151124716.png){:height 252, :width 658}
				- 通过 Reflection 之后得到了比**Problem Description**更加清晰、连贯的信息，从而更加有利于生成解决方案。
				  ![](https://raw.githubusercontent.com/stillfox-lee/image/main/picgo/202504151125758.png)
			- **公共测试推理 (Public tests reasoning)**
				- 解释为什么每个测试输入会导致对应的输出。
			- **生成可能的解决方案 (Generate possible solutions)**
				- 生成一个包含 2-3 个问题可能解决方案的列表，用自然语言描述。
			- **对解决方案排序 (Rank solutions)**
				- 对可能的解决方案进行排序，并选择“最佳解决方案”，考虑其正确性、简单性和鲁棒性。（不一定选择“最高效”的解决方案）。
			- **生成额外的 AI 测试 (Generate additional AI tests)**
				- 为问题额外生成 6-8 个多样化的输入输出测试。尝试覆盖原始公共测试未覆盖的情况和方面。
		- **Code interations** 阶段
			- 针对公共测试集和 AI 生成测试集，进行`代码生成`、`运行代码`、`修复代码`
			- **初始代码解决方案 (Initial code solution)**
				- 此阶段的目标是生成问题的初始代码解决方案。至关重要的是，这个代码要合理地“接近”正确的代码，这样后续阶段的run-fix迭代才有更高的成功机会。
				- 阶段流程如下：
				  • 选择一个潜在的解决方案。生成相应的代码，并在选定的公共测试和 AI 测试上运行它。
				  • 重复此过程，直到测试通过，或达到尝试次数限制。
				  • 第一个通过测试的代码，或者输出最接近的代码（参见附录 D），将用作后续步骤的基础代码。
			- **基于公共测试进行迭代 (Iterate on public tests)**
				- 从基础代码开始。在公共测试上迭代运行它。如果代码在特定测试上失败，尝试根据错误消息修复它。
			- **基于 AI 生成的测试进行迭代 (Iterate on AI-generated Tests)**
				- 继续在 AI 生成的测试上进行运行-修复迭代。使用“测试锚点”（test anchors）
		- *这个 Flow Engineering 相较于单个直接的 Prompt 效果能得到提升。*
	- AlphaCodium flow总结的一些技巧和最佳实践：
		- (1)YAML 结构化输出；
		- (2) **通过要点分析进行语义推理** bullet point analysis to encourage semantic reasoning;
			- 当要求 LLM 对某个问题进行推理时，如果要求输出采用要点（bullet points）格式，会获得更好的结果。要点鼓励对问题进行深入理解，并迫使模型将输出划分为逻辑语义部分，从而改善结果。例如，通过要点进行Problem Reflection 时（图 2 (b)），每个要点代表了对问题不同部分的语义理解——总体description、goal和rule、input结构以及output 结构。
		- generating modular code;
			- 当要求 LLMs 生成单个冗长的函数时，我们观察到结果不佳——代码通常包含错误或逻辑错误。更糟糕的是，单个庞大的代码会损害执行迭代修复的能力——即使给出错误消息，模型也很难查明和修复问题。当明确要求模型：**“将生成的代码划分为小型子函数，具有有意义的名称和功能”**时，我们观察到生成的代码更好，错误更少，并且迭代修复阶段的成功率更高。
		- **使用双重验证进行软决策** soft decisions with double validation;
			- LLMs 在处理需要它们思考、推理并做出严格、非平凡决策的代码任务时往往会遇到困难。以生成问题的额外测试为例。模型生成的某些测试通常会是完全错误的。通过双重验证过程，我们增加了一个额外步骤：给定生成的输出，要求模型重新生成相同的输出，但如有需要则进行修正。例如，给定生成的 AI 测试作为输入，要求模型重新生成相同的测试，同时修正存在的错误输出。我们发现，这种双重验证步骤，在**鼓励模型进行批判性思考和推理**的同时，比直接问一个“是/否”问题：“这个测试正确吗？”更有效。
		- **推迟决策，尽量避免直接提问，并为探索留出空间 (Postpone decisions, try to avoid direct questions, and leave room for exploration):**
			- 当我们就复杂问题向模型提出直接问题时，我们持续看到幻觉和错误答案。为了应对这种情况，我们采用了一种`从易到难逐步积累数据`的流程：
			- • 从最简单的任务开始——对问题进行自我反思，以及对公共测试进行推理。
			  • 接着生成额外的 AI 测试，以及问题的可能解决方案。
			  • 只有在我们获取了模型对上述任务的答案之后，我们才转向实际的代码生成和运行-修复迭代。
		- **测试锚点 (Test anchors):** 即使进行了双重验证，一些 AI 生成的测试仍然会是错误的。这使得基于它们的迭代变得具有挑战性——当一个测试失败时，我们怎么知道是因为代码错了，还是因为测试错了？当我们直接问模型“谁错了”时，我们经常看到幻觉，并可能最终得到错误修复的代码。为了解决这个问题，我们利用了一种称为“测试锚点”的技术：
			- • 首先在公共测试上进行迭代，我们知道这些测试是正确的。完成后，将所有通过的测试设置为锚点测试。
			  • 现在逐一在 AI 生成的测试上进行迭代。如果一个测试通过，将其添加到测试锚点列表中。
			  • 如果一个测试失败，假设是因为代码不正确，并尝试修复代码。但是，要求修复后的代码也必须通过所有已获取的测试锚点。结果，测试锚点将保护我们免受错误修复代码的影响。
			- 测试锚点的另一个优化是将 AI 生成的测试从易到难排序。这样，迭代过程更有可能在开始时获取锚点，这些锚点可以在稍后迭代更复杂的 AI 测试时用作保护。
	- Insight 和构建这个 AlphaCodium flow 的直觉
		- 首先，该流程依赖于知识积累——试图从易到难逐步推进，在此过程中获取知识和洞察力，以帮助应对更困难的阶段。例如，第一步“Problem Reflection”的**输出**可以用作更困难步骤（如“Generate possible solutions”）的 prompt **输入**。预处理阶段的输出用于辅助最具挑战性和最关键的阶段——代码迭代，在这一阶段我们尝试生成能正确解决问题的代码。
		- 另请注意，某些步骤可以合并到单个 LLM 调用中，图 2(a) 中的流程是一个概念流程，强调了过程的高级步骤。在实践中，结构化输出（参见第 4 节）使得可以将多个阶段合并到单个 LLM 调用中，以节省资源，或者因为模型在同时执行特定任务时表现更好。
	- ## 精华总结
		- 使用bullet points。让 llm 对 Problem 进行总结，可以鼓励模型更好思考。
		- double validate。通过提供上一次的结果，再次生成，同时有问题则修复。同时完成 double check。
		- 避免一次出结果。从易到难逐步积累 context 数据。
