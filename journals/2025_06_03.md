- Graph-Guided LLM Agent for Code Localization ![LocAgent.pdf](../assets/LocAgent_1748920291076_0.pdf) #paper
	- 摘要
		- > 我们引入了 LOCAGENT，一个通过基于图的表示来解决代码定位问题的框架。通过将代码库解析为有向异构图 (directed heterogeneous graphs)，LOCAGENT 创建了一个轻量级表示，捕捉了代码结构（文件 (files)、类 (classes)、函数 (functions)）及其依赖关系（导入 (imports)、调用 (invocations)、继承 (inheritance)），使得 LLM agent 能够通过强大的多跳推理 (multi-hop reasoning) 有效搜索和定位相关实体。在真实世界基准测试 (benchmarks) 上的实验结果表明，我们的方法显著提高了代码定位的准确性 (accuracy)。值得注意的是，我们的方法使用微调 (fine-tuned) 的 Qwen-2.5-Coder-Instruct-32B 模型，以大幅降低的成本（约减少`86%`）达到了与SOTA (state-of-the-art) 专有模型相媲美的结果，在文件级定位 (file-level localization) 上准确率高达`92.7%`，同时将下游 GitHub issue 解决的多尝试成功率`(Pass@10)`提高了`12%`。
	- ## 引言
		- Dense 方式检索代码需要维护和持续更新整个代码库的向量，这给大型、快速演化的代码库 (repositories) 带来了工程挑战，因为代码会频繁更改。
		- 此外，`Issue`通常只提及**症状**而非**根本原因**。Issue描述与受影响代码组件之间的这种脱节对传统检索方法构成了重大挑战，这些方法难以追踪代码库结构中隐含的依赖关系。
		- 通过 `directed heterogeneous graph indexing` 索引代码结构，依赖以及代码内容。
		- 和已有方案对比的主要贡献：
			- 引入了一种异构图表示 (heterogeneous graph representation)，它捕获了显式和隐式的代码关系，从而实现了高效的多跳推理。我们的轻量级基于图的索引过程每个代码库仅需数秒，并且需要最少的存储空间。
			- 基于 agent 的代码探索设计了统一的工具，这些工具利用了我们的图表示，使 LLM agent 能够跨代码依赖关系执行复杂的多跳导航和推理，即使目标代码未在问题描述中明确提及。
			- 引入了 Loc-Bench，一个专为代码定位设计的新基准测试，解决了现有数据集的局限性。与以往主要由 bug 报告主导的基准测试不同，Loc-Bench 在 bug 修复、功能请求、安全补丁和性能优化之间提供了均衡的分布。
			- 通过在此任务上微调开源模型，我们将代码定位的成本降低了`86%`，同时保持了有竞争力的性能。
	- ## 相关工作
		- 传统检索方法
			- 方案：
				- Sparse retrievers (BM25)
				- Dense retrievers (Embedding 模型)
			- 挑战：在于维护这个索引的工程量比较大，代码变更是非常频繁的。
		- 基于 LLM的 搜索增强
			- 方案：
				- `OpenHands` 基于`grep`、`bash`这类 tools
				- `SWEAgent` 通过自定义 Agent-Computer Interface，以支持 agent 导航整个代码库
				- `MoatlessTools` (Örwall, 2024) 结合了一个 agentic searching loop 和语义搜索 (semantic search) 来获取代码位置。
			- 挑战:
				- (a) 它们主要通过目录遍历来导航代码库，而不是理解语义关系，
				- (b) 当这些关系未在代码库结构中明确表示时，它们难以提取和推理复杂的跨文件依赖关系。这严重削弱了当问题涉及代码库中结构上相距较远的组件之间的交互时，它们定位需要修改的代码的能力。
		- 基于图的代码表示
			- 方案：
				- `Aider` 的 RepoMap
				- `RepoGraph`
					- 执行子图检索 (subgraph retrieval)——提取相关代码行及其邻居的自我网络 (ego-network)——以提供结构化上下文
				- `CodexGraph`
					- 将代码库索引到一个 Neo4j 图数据库中，LLM agent 使用 Cypher 精确查询该数据库
			- 挑战：
				- 其检索过程的效率在很大程度上取决于 LLM 的查询能力。这些方法主要侧重于提供相关上下文，但并未增强遍历过程本身，因为它们没有明确地对**目录结构**或**文件层次结构**进行建模。
			- `RepoUnderstander` (Ma et al., 2024) 构建了层次图和函数调用图 (function-call graphs)，并使用由 LLM引导的蒙特卡洛树搜索 (Monte Carlo Tree Search, MCTS) 进行探索。虽然详尽，但 MCTS 引入了额外的计算开销，使其效率低于像 BFS 这样更简单的遍历方法，尤其是在大型代码库中。
			- `OrcaLoca` (Yu et al., 2025) 使用一个简化的图，并通过优先级调度和上下文修剪进行增强。它保持了高效的搜索，但可能会遗漏复杂的调用依赖。
	- ### LocAgent 框架
		- 整体结构
		  ((683e9934-2437-425d-b986-4d2dbc7c509e))
		- #### Graph-based Code Representation
			- 用一个 `heterogeneous directed graph` 来索引整个代码库。有一个 Node Set 和一个 Edge Set，每个 Node 和 Edge 都有一个关联的类型映射函数。**Node** 会映射为：`{directory,file,class,function}`，**Edge** 会映射为：`{contain, import,invoke,inherit}`。*当前只索引 Python，其他语言需要另外映射*。
		- 建立索引的过程：
			- **构建 Node**：把所有的 directory 和 file 作为 Node，然后解析每个文件的 AST，识别其中的 class 和 function 作为 Node。将每个 function 的代码作为检索内容。
			- **构建 Edge**：所有不同类型的节点都可以通过包含 (contain) 关系连接成单个树状结构。这种结构支持现有工作中标准的基于代码库的导航操作。我们的代码图进一步整合了更高级的代码库关系作为边：(1) 从函数/类到函数/类的调用 (invoke) 关系，其中对类的调用表示类实例化；(2) 从文件到函数/类的导入 (import) 关系；以及 (3) 类之间的继承 (inherit) 关系。
			- **稀疏层次化实体索引 (Sparse Hierarchical Entity Indexing)**
				- 将所有的 Node 作为 Entity，并基于其内容构建层次化索引。索引会分为 4 层。
				- 分层索引：
					- 第一层：Entity ID 索引
					  使用每个 Node 的完全限定名称 (fully qualified name) 构建一个 Entity ID 索引 (entity ID index) 作为其唯一标识符。
					- 第二层：全局字典
					  将实体名称（例如 calculate_sum）映射到所有共享相同名称的节点
					- 第三层：BM25 倒排索引
					  通过倒排索引 (inverted index)（即 BM25）索引实体 ID，以处理与实体 ID 或名称不完全匹配的关键词搜索。
					- 第四层：代码块倒排索引
					  对于输入关键词不属于实体 ID 的情况（例如，当关键词引用全局变量时），我们构建一个将代码块 (code chunk(s)) 映射到每个实体的倒排索引，以覆盖所有可能的匹配。
				- 提供的 Tool
					- ```
					  SearchEntity(Keywords) return (Related Entites with Code Snippets)
					  TraverseGraph
					  RetrieveEntity
					  ```
		- 构建 Agent 的Code Search
			- 面向 Agent 设计的 Tool：
				- `SearchEntity`：此工具使用关键词 (keywords) 通过我们的层次化实体索引 (Hierarchical Entity Index) 搜索代码库以定位相关实体。当在上层索引中未找到精确匹配时，系统将使用下层索引执行模糊搜索 (fuzzy search)。对于找到的每个实体，我们以三种详细级别返回其代码片段：折叠 (fold)、预览 (preview) 和完整代码 (full code)（图 6）。这有效地防止了过长的代码上下文并减少了输入给 agent 的噪声。
				- `TraverseGraph`：此工具在代码图上执行类型感知的广度优先搜索 (Breadth-First Search, BFS)，从输入实体开始，并允许控制遍历方向和跳数 (hops)。这支持 agent 仅通过一个动作执行任意的多跳代码库导航，与现有 agent 系统相比，显著提高了效率。请注意，通过允许 agent 为每次遍历选择实体类型和关系类型，此工具有效地利用了 LLM agent 的编码专业知识来生成适当的元路径 (meta paths)——这是异构图分析的关键元素 (Lv et al., 2021)。例如，通过将实体类型指定为 {class, function} 并将关系类型指定为 {contain, inherit}，此工具返回 UML 图。此外，我们为输出子图设计了一种扩展的基于树的格式，该格式编码了关系类型和方向（图 7）。(Fatemi et al., 2023) 表明 LLM 在图推理上的性能取决于输入图的格式。将图转换为树结构通过实体名称之间的空间距离编码拓扑结构，从而获得更好的性能。有关替代图格式的详细比较，请参见附录 A.1.2。
				- `RetreiveEntity`：此工具为每个输入实体 ID 检索完整的实体属性，包括文件路径、行号和代码内容等基本信息。
